작성일: 2026-10-19 (같은 날 UI 시안 반영·구현 결과에 맞춰 갱신)
기준 문서: [서비스기획_정리.md](서비스기획_정리.md) (무엇을 보여 줄지), [검증결과_10년.md](검증결과_10년.md)·[리허설_검증.md](리허설_검증.md) (계산 정의와 근거)

> 이 문서는 **구현을 마친 상태**를 기준으로 씁니다. 화면 구성은 UI 시안(CareOps 운영 대시보드)을 우리 기획의 필수 항목에 맞게 바꿔 반영했습니다 (8장).

## 1. 설계 원칙

| 원칙 | 내용 |
|---|---|
| 무거운 계산은 미리 | 예측·모델 학습은 기준일마다 미리 계산해 저장(`engine.build`). 시연 중에는 읽기와 가벼운 합산·분류만 |
| 검증한 계산 = 화면 계산 | 검증 스크립트(`analysis/`)의 계산 중 화면에 쓰는 것을 `engine/` 패키지로 옮김. 사전 계산 끝에 **시나리오 결과를 리허설 표와 자동 대조**하고, 다르면 실패 처리 (6.3) |
| 과거 시점 재현이 기본 | 모든 화면 값은 "기준일까지 알려진 데이터 + 그날 발표된 예보"로만 계산. 기준일만 바꾸면 과거 어느 주로든 돌아감 |
| 오프라인 동작 | 외부 CDN·API 호출 없음 (글꼴 Pretendard·ECharts·데이터 모두 로컬). 서버 하나(`uvicorn`)로 화면까지 제공 |
| 설명 가능 | 각 구역의 ⓘ·"근거 보기"에서 검증 수치와 계산식을 바로 확인. 인력 환산은 계산식을 화면에 그대로 표시 |

## 3. 전체 구조

```
                         ┌──────────────── 오프라인 (사전 계산, 약 3분) ────────────────┐
data/raw/  ──pipelines/──▶ data/processed/ ──engine.build──▶ data/artifacts/*.parquet (약 3MB)
(311, 기상, 예보)          (병합·변수)       └ 리허설 대조   + manifest.json (기준일·시나리오·근거)
                         └───────────────────────────────────────────────────────────────┘
                                                                   │ 서버 시작 때 메모리로 (pandas)
                         ┌────────────────── 시연 서버 ───────────▼──────────────┐
                         │ FastAPI (backend/app)  /api/...  /docs                │
                         │   └ 가벼운 계산: 기간 합산, 매트릭스 분류, 인력 환산    │
                         │ React 빌드 결과(frontend/dist)를 같은 서버 / 에서 제공 │
                         └───────────────────────────────────────────────────────┘
```

사전 계산 결과가 작아(약 3MB) DuckDB 없이 서버 시작 때 Parquet을 모두 메모리에 올립니다. 기준일별 계산 결과는 첫 요청 때 만들어 캐시합니다.

## 5. 계산 엔진 (engine/)

모든 함수는 `asof`(기준일)를 받아 **그 이전 데이터만** 씁니다. 정의는 검증 문서와 같아야 하며, 다르면 검증 문서를 먼저 고칩니다.

| 모듈 | 입력 | 출력 | 정의 (근거 문서) |
|---|---|---|---|
| forecast_short | 일별 부서 건수, 공휴일 | 1~7일·8~14일 부서별 합계, 80% 범위 | LightGBM, 기준일 전에 끝난 블록으로만 학습. 범위 = 연 단위 재학습 백테스트 오차의 10~90% 지점 (검증 ②) |
| forecast_long | 월별 부서 건수 | 월별 부서 예측, 80% 범위 | 계절 지수(과거 최대 7년 중앙값) × 직전 3개월 계절 보정 수준. 범위 = 2019년부터 같은 방식 과거 오차 (검증 ①) |
| alerts | 시간별 예보(1·2·3·5·7일 전 발표분), 관측 | 날짜별 특보 단계, 특보 영향 부서 | NWS 뉴욕 지청 기준. 기준일+k일은 k일 전 발표 예보(4일→5일 전, 6일→7일 전) (검증 ⑩) |
| issues | 일별 이슈 건수, 관측 기상 | 같은 달 급증 빈도, 도로 파손 전망 | 급증 = 직전 12개월 평균의 1.5배·30건 이상. 겨울 적설 → 3~4월 배수, 1.5배 이상이면 표시 (검증 ⑤) |
| backlog | 민원 1건별 | 처리 중 민원 수, 적체 배수, 최근 4주 일평균, 즉시 종결 비율 | 적체 배수 = 처리 중 ÷ 직전 52주 중앙값 (리허설 3장) |
| risk | 민원 1건별 변수 | 처리 중 민원의 지연 확률, 순위, 주요 요인 | 로지스틱 회귀, 매달 1일 최근 12개월로 재학습. 소비자보호국은 경과일 ÷ 기준처리기간 (검증 ⑥) |
| dashboard.matrix | 기간 예측, 적체 배수, 특보 표시 | 부서별 가로·세로·사분면·범위 | 가로 = 기간 일평균 ÷ 최근 4주 일평균 − 1. 기준 +10%·1.3배, 지원 가능 = −10% 이하·적체 기준 미만. 특보·도로 파손 부서는 지원 가능에서 제외(→ 안정) (리허설 2장) |
| dashboard.staffing | 매트릭스, 가정값 | 적체 증가 건수, 필요 인원, 지원 가능 부서 여유, 짝 | (예상 − 평소) × (1 − 즉시 종결 비율) × 적체 전환율, 접수 +10% 이상 부서만. 인원 = 건수 ÷ (1인 하루 처리 × 근무일) (검증 ⑨) |

**처리 중 민원 판정:** 최근 6개월 접수분 중 `종결일 없음` 또는 `종결일 ≥ 측정일` 또는 `상태 ≠ Closed`. (상태가 Open·Assigned인데 종결일이 찍힌 민원이 있어(전체 3,434건, 건축국 최근 6개월분 1,256건) 상태 조건을 더함 → 건축국 최신 적체 배수 0.13배 → 0.79배로 정상화)

**기간 예측 합치기 규칙**
- 기간 끝이 기준일 + 13일 안: 단기 모델. 1~7일 블록·8~14일 블록 예측을 최근 8주 요일 비율로 날짜에 나눠 합산. 80% 범위는 끝이 7일 안이면 1~7일 블록, 넘으면 8~14일 블록의 오차 비율
- 그보다 길면: 기간 전체를 월별 방식으로 (월 예측을 그 달 날짜에 요일 비율로 나눠 합산), 범위는 월별 오차 비율
- 기상 특보 영향 부서: 범위 상한 = max(상한, 예측 + (배수 − 1) × 특보가 걸친 날의 예측). 배수: 환경보호 1.6, 공원·위생 3.1, 그 외 2.6
- 봄철 도로 파손(교통국): 범위 상한 + 하루 추가분 × 3~4월과 겹치는 날 (추가분 = (배수 − 1) × 평소 월 건수 × 2 ÷ 61)

## 6. 사전 계산 (engine.build)

### 6.1 실행 순서
1. 기준일 목록 생성 (월요일 141개 + 시나리오 날짜 4개 = 145개)
2. 공통 준비: 단기 학습 행·백테스트, 월별 과거 예측, 특보 단계(관측·예보), 월별 이슈, 주별 적체
3. 기준일마다: 단기 예측 → 월별 예측(92일) → 오차 비율 → 특보·영향 부서 → 도로 파손 → 이슈 빈도 → 부서 상태 → 지연 위험 목록
4. 지연 위험 모델은 **달마다 한 번** 학습해 그 달의 기준일들이 같이 씀
5. 표마다 Parquet으로 저장하고 `manifest.json`(실행 시각, 코드 버전, 기준일, 시나리오, 근거 문구) 기록

실행 시간: 맥북 기준 **약 3분(185초)**.

### 6.3 정확성 확인 (빌드 끝에 자동 실행)
- 시나리오 S1~S4의 부서별 예측·범위·적체 배수·사분면·80% 범위 포함 여부를 [리허설_검증.md](리허설_검증.md)의 표(`analysis/results/rehearsal_matrix.csv`)와 대조
- 현재 결과: **4개 시나리오 모두 차이 0.00%, 사분면 32/32 일치** → 검증한 계산과 화면 계산이 같음
- 다르면 빌드 실패. (단기 모델은 학습 행 순서가 결과에 영향을 줘서, 행 정렬을 검증 스크립트와 같게 고정)

## 7. API 설계 (FastAPI)

공통 쿼리: `asof`(목록에 있는 날짜만), `start`·`end`(기준일 이후, 최대 92일, 없으면 7일), `agency`(선택, 없으면 전체)

| 메서드·경로 | 응답 내용 | 계산 |
|---|---|---|
| `GET /api/meta` | 부서 목록, 기준일 145개, 최신일, 시나리오 5개, 기간 빠른 선택, 매트릭스 기준값 | 저장값 |
| `GET /api/summary` | 상단 지표 5개: 예상 접수, 기상 특보, 집중관리 부서(부서 선택 시 판정), 처리 중 민원, 지원 필요 인원 | 합산 |
| `GET /api/forecast` | 기간 합계·80% 범위·실제값(지난 기간), 부서별 값, 추이(31일 이하 일 단위, 넘으면 주 단위) | 기간 합산 |
| `GET /api/issues` | 특보 목록(관측·예보), 이슈 카드, 머리 문구, 같은 시기 급증 빈도, 도로 파손 전망, 실제 급증 | 저장값 필터 |
| `GET /api/matrix` | 부서별 x·범위·y·사분면·특보 표시·처리 중 수, 실제값(지난 기간) | 요청 시 분류 |
| `GET /api/staffing?per_person_day=10` | 적체 증가 부서·필요 인원, 지원 가능 부서·여유, 짝, 충당률 | 요청 시 계산 |
| `GET /api/risk-list?limit=15` | 지연 위험 민원 (부서 선택 시 그 부서 순위, 전체면 부서마다 상위 2건) | 저장값 |
| `GET /api/evidence` | 구역별 검증 수치와 출처 | 저장값 |
| `GET /api/health` | 서버·데이터 파일 상태 | |

**응답 예시: `/api/matrix?asof=2026-02-20&start=2026-02-20&end=2026-02-26` (일부)**

  "thresholds": {"x": 0.1, "y": 1.3, "support_x": -0.1},

- 응답 형식은 `schemas.py`(Pydantic)로 정의 → `npm run gen:api`가 OpenAPI에서 **프런트 타입을 자동 생성**
- 민원 유형은 뉴욕 원문(`complaint_type`)과 화면 표기(`type_ko`, 53종 한글)를 함께 보냄

**오류 처리:** 목록에 없는 기준일·92일 초과·순서가 틀린 기간은 400과 한국어 메시지. 사전 계산 결과가 없으면 503("`uv run python -m engine.build`를 먼저 실행하세요").

## 13. 실행 방법

```bash
# 1) 사전 계산 (처음 한 번, 약 3분) — 끝에 리허설 대조 결과가 나옴
uv run python -m engine.build

# 2) 화면 빌드 (처음 한 번, 화면 코드를 바꾼 뒤)
cd frontend && npm install && npm run build && cd ..

# 3) 시연 서버 — http://127.0.0.1:8000 에서 화면, /docs 에서 API 문서
uv run uvicorn app.main:app --app-dir backend
```

개발 중에는 `uv run uvicorn app.main:app --app-dir backend --reload`와 `cd frontend && npm run dev`(5173번, /api는 8000번으로 전달)를 함께 띄웁니다. API 응답 형식을 바꾸면 `npm run gen:api`로 타입을 다시 만듭니다.
